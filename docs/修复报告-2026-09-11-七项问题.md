## P0-1 投屏黑屏 + 远程控制「获取控制诊断失败」

### 现象
1. 日志报 `RemoteControl 获取控制诊断失败: Tried to obtain display from a Context not associated with one`。
2. 无障碍已在系统里开启，App 里却显示未生效；远程触控点哪都没反应。
3. 偶发投屏连接成功后 Web 端画面全黑，不再恢复。

### 根因
1. **Display 取错了 Context**：`RemoteControlService` 是 `AccessibilityService`，直接用 `this`（Service base Context）或 `applicationContext` 取 `WindowManager` / `Display`。Service/Application 的 base Context **没有关联可视化 Display**，系统直接抛
   `Tried to obtain display from a Context not associated with one`。
2. **分辨率返回 0x0 的连锁反应**：取 Display 失败后走异常分支返回 `0x0`，Web 端做坐标映射时按比例算出 `(0,0)`，
   点击全部落在左上角——表现为「无障碍已开但触控无效」，实际是分辨率数据错误，不是触控注入失败。
3. **无障碍状态用错了信号**：原来把 `settingsEnabled`（系统设置里开关状态）当成「已生效」。
   国行 ROM 上 `AccessibilityManager.getEnabledAccessibilityServiceList` 常查不到、`Settings.Secure` 普通应用无权限读，
   导致「已开启」被误判为「未开启」；反过来开关关了但服务实例还在，也会误判为已生效。
   **真正可靠的信号是服务实例是否被绑定（connected）。**
4. **黑屏**：`onTrack` 回调可能早于 `<video>` 元素挂载（组件异步渲染），此时流被丢弃后再无人补绑，`srcObject` 永久为空；
   另一类是编码侧卡死（ICE 完成后 track 实际未输出帧），但连接状态仍是 `connected`，前端无从感知。

### 修改

## P0-2 文件传输取消后 App 端出现空白文件、状态不同步

### 现象
Web 端取消传输后，App 端聊天列表出现一条 0 字节的文件消息；Web 显示已取消，App 仍显示传输中；断开连接后残留半成品文件。

### 根因
1. **取消后会话被在途数据「复活」**：取消只是置了标志，网络侧仍在收 chunk，`_handleChunk` 照常处理并重新进入组装流程，最终生成空文件。
2. **空组装不设防**：`_assembleFile` 对「收到 0 字节」的情况照样落库成文件消息，产生空白记录。
3. **没有回执**：Web 端不知道 App 是否已清理，双方状态各说各话。
4. **断开连接未在途清理**：`disconnect()` 未对进行中的收发任务做收尾。

### 修改
| 文件 | 说明 |
| --- | --- |
| `flutter-app/lib/services/message_service.dart` | ① 新增 `_cancelledTransfers` 集合，`_handleFileStart` / `_handleChunk` 命中即**提前 return**，杜绝复活；② `_cancelReceive()` 重写：移除 meta → 加入取消集合 → 清速率状态 → 删除半成品文件 → 发送 `cancel_ack` → 抛 `{'cancelled': true}` 进度；③ 新增 `_sendCancelAck()`；④ `cancelSend()` 对称清理 `_pendingSends` / `_fileMetas` / 定时器；⑤ `_assembleFile` 遇到 `totalBytes == 0` 判定为取消，**不落文件**；⑥ `disconnect()` 对在途任务抛 `interrupted`；⑦ `dispose()` 清理取消集合 |
| `flutter-app/lib/utils/partial_file.dart`<br>`partial_file_io.dart` / `partial_file_stub.dart` | 新增条件导出工具，安全删除 `.part` 半成品文件（web 端 stub 空实现） |
| `flutter-app/lib/providers/message_provider.dart` | 处理 `cancelled == true` → 状态置 `MessageStatus.cancelled`，保留最后一次进度，标记完成并清空速率/ETA |
| `flutter-app/lib/screens/message_screen.dart` | 取消按钮对**发送和接收**双方都可见（原来只有发送方可取消） |
| `pc-web/src/composables/useMessageTransfer.js` | 新增 `cancel_ack` 处理 `_handleCancelAck`；`_handleCancel` / `cancelTransfer` 同步清理 `_fileReceivedCount`、`_fileSpeedSample`、`_fileReceivedBytes`、`_fileRateWindow`、`_pendingChunks`，速率与 ETA 归零 |

### 验证步骤
1. Web 发送大文件（>50MB）→ 传输中点取消：App 端应显示【传输已取消】，**聊天列表不新增任何文件消息**。
2. 检查 App 沙箱目录（`adb shell run-as com.example.ai_cast_hub ls files/`）：不应残留 `.part` 半成品。
3. Web 端应收到 `cancel_ack`，任务从传输列表消失，速率显示清空。
4. 反向测试：App 发送、Web 取消 → App 端同样置为已取消且不产生残留。
5. 传输中途断开 WebRTC / 杀掉一端：在途任务应显示 interrupted 而非卡在传输中。

## P1-6 服务监控服务状态智能识别

### 现象
监控面板显示的状态与实际不符：进程还在却显示未运行；启动失败和异常退出都显示「已停止」；点了启动后要手动刷新才知道结果。

### 根因
原实现以 **PID 存在 + 退出码** 为唯一判据。PID 文件可能残留（进程已死但 PID 还在）、端口被其他进程占用（服务没起来但端口 LISTEN）、进程是同名的其他脚本（cmdline 不匹配）；`exit code` 只在启动瞬间有效，不能代表长期运行状态。

### 修改
| 文件 | 说明 |
| --- | --- |
| `server/src/modules/server-monitor/util.js` | 新增 `probeHttp(port, path, timeoutMs)`（HTTP 健康探测）、`readCmdline(pid)`、`processMatchesScript(pid, script)`（cmdline 匹配，排除同名进程） |
| `server/src/modules/server-monitor/processManager.js` | ① `getStatus()` **改异步**，多维度判定：端口 LISTEN → 进程存活 + **cmdline 匹配** → HTTP/TCP 健康探测 → 关联 nginx 的 `proxy_pass` 端口检查；② 新增五态 `SERVICE_STATUS`：`stopped / starting / running / start_failed / crashed` + `STATUS_TEXT`；③ 新增 `_statusListeners` / `onStatusChange()` / `_emitStatusChange()`；④ `start()` 置 `phase: 'starting'`，注册 `child.on('exit')` 判定 crashed / start_failed 并推送；⑤ `_startStartupWatcher()`：启动后**最多 30 秒、1 秒轮询**，状态实时推送；⑥ 退出码仅作启动阶段参考 |
| `server/src/modules/server-monitor/serviceAggregator.js`<br>`routes.js` | 同步 `await processManager.getStatus(...)`（异步化后的调用点适配） |
| `server/src/modules/server-monitor/wsHub.js` | 新增 `registerProcessStatusListener()`，轮询前注册，状态变化广播 `service_status` |

3. 启动不存在的入口脚本：应显示**启动失败**，且 30 秒内实时推送，无需刷新页面。

5. 启动超过 30 秒未就绪：应给出明确失败/超时状态。
6. 用同名但不同脚本的进程占用端口：cmdline 不匹配，不应误判为运行中。
7. 关联了 nginx 的服务：额外校验 `proxy_pass` 端口，nginx 未代理时给出提示。

## 约束遵守情况

- 未引入任何新的重型第三方依赖（新增能力均用 Node 内置 `fs/net/http`、Dart 标准库、Vue 现有能力实现）。
- 所有新增逻辑均做了异常兜底：`getScreenSize` 不返回 0x0、诊断接口 try/catch、持久化写入失败不影响主流程、
  监控探测超时有上限、消息通道建链失败可重试。
- 密钥自动绑定与指令执行沿用原有鉴权与白名单，未放宽任何校验。
